# [MCP 회고] AI 잡으려고 만든 검사기가 처음 잡은 건 제 문서였습니다

안녕하세요, 디자인 시스템 [7onic](https://7onic.design)을 만들고 있는 개자이너입니다.

문서와 코드가 어긋난 곳을 찾는 검사기를 새로 만들고 처음 전체를 돌려 봤더니, 제 디자인 시스템에서 에러가 122개 나왔습니다.

그중 119개 정도는 제 파서 탓이었습니다. 문서에 적힌 "Select.Trigger"와 코드의 `SelectTrigger`가 같은 거라는 걸 파서가 몰랐다든지, 그런 종류였습니다. 파서를 고치고 다시 돌리니 에러가 3개 남았습니다. 셋 다 진짜 문제였고, 셋 다 `llms.txt`에 있었습니다. 제가 공들여 관리해 온 이 문서를 읽은 AI 도구들이 그동안 틀린 내용을 배우고 있었다는 뜻입니다.

- Badge 문서에 `radius` 값으로 `xl`이 적혀 있었습니다. 컴포넌트에는 한 번도 없던 값입니다. 반대로 실제로 있는 `base`는 빠져 있었습니다.
- Chart 예제의 import 줄에 정작 `Chart`가 없었습니다. 그대로 복사해서 쓰면 첫 렌더링부터 "정의되지 않음" 에러가 납니다.
- `DropdownMenu.RadioGroup`은 배포한 지 몇 달이 지났는데 문서에 아예 없었습니다.

AI가 규칙을 어기는 걸 잡으려고 만든 도구였는데, 처음 잡아낸 건 AI에게 틀린 정보를 주고 있던 제 문서였습니다.

<br />

## 문서만으로는 부족했던 이유

[예전 글](https://blog.7onic.design/using-ai-to-build-a-design-system/)에서 `llms.txt` 이야기를 한 적이 있습니다. AI 도구가 컴포넌트 API와 토큰 규칙을 알 수 있도록 여섯 가지 버전으로 관리하는 문서입니다. 그 글 끝에 적은 관찰 하나가 계속 마음에 걸려 있었습니다. 작업 세션이 길어지면, 처음에는 잘 지키던 규칙을 어느 순간부터 슬그머니 안 지킨다는 점입니다. 일부러 어기는 게 아니라 점점 잊어버리는 쪽에 가깝습니다.

문서라는 방식 자체의 한계입니다. 문서는 결국 "이렇게 해 주세요"라는 부탁입니다. AI는 문서를 읽고 수긍하지만, 작업을 네댓 개 하고 나면 `bg-blue-500`을 아무렇지 않게 씁니다. 쓰지 말라는 내용이 이미 관심 밖으로 밀려났기 때문입니다. 문장을 더 잘 쓴다고 해결되지 않습니다. 문서에는 "안 돼"라고 막을 수단이 없으니까요.

그래서 9월 30일부터 10월 7일까지 규칙을 강제하는 쪽을 만들었습니다. MCP 서버입니다. MCP(Model Context Protocol)를 쓰면 AI가 글을 읽기만 하는 게 아니라 도구를 직접 호출할 수 있습니다. 별 차이 없어 보이지만 완전히 다릅니다. 문서는 토큰 시스템을 설명할 뿐이고, 도구는 지금 이 순간의 값을 바로 알려 주는 토큰 시스템 그 자체입니다.

<br />

## 서버가 하는 일

도구는 9개인데, 핵심은 세 가지입니다.

**`suggest_tokens`는 하드코딩을 막는 도구입니다.** AI가 `#FF5733` 같은 값을 쓰려고 하면 먼저 이 도구에 물어보게 되어 있습니다. 도구는 OKLab 색 거리로 가장 가까운 실제 토큰을 알려 줍니다. 이 경우에는 ΔE 0.053인 `red-500`이라 가깝지만 똑같지는 않습니다. 정확히 맞는 토큰이 없을 때 "가장 가까운 걸 쓰세요"라고 답하지 않는다는 게 포인트입니다. 대신 토큰 시스템을 벗어나도 되는지 사용자에게 물어보라고 지시합니다. 그건 원래 AI가 혼자 정할 일이 아니니까요.

**`validate_code`가 제가 정말 만들고 싶었던 도구입니다.** AI가 만든 TSX를 넣으면 코드 구조(AST)를 분석해서 className을 전부 꺼냅니다. `cn()` 안이나 템플릿 리터럴 안에 숨어 있는 것까지 꺼냅니다. 그다음 규칙 14개로 검사합니다. 기본 팔레트 색을 그대로 썼는지, 임의 값을 넣었는지, `dark:` 접두사를 썼는지(시맨틱 토큰은 테마에 따라 알아서 바뀝니다), `leading-*`로 줄 높이를 덮어썼는지(타이포그래피 토큰에는 글자 크기와 줄 높이가 같이 들어 있습니다), 인라인 스타일을 썼는지, 컴포넌트가 있는데 `<button>` 같은 HTML 요소를 그대로 썼는지 같은 것들입니다. 위반이 나오면 줄 번호와 수정 방법을 영어, 일본어, 한국어로 알려 줍니다.

**세 번째는 도구라기보다 데이터를 만드는 과정입니다.** 서버가 아는 컴포넌트 정보는 전부 `llms-full.txt`에서 만들어지고, 다른 원본 세 곳과 서로 대조됩니다. 실제 소스의 export, CVA variant 정의, CLI 레지스트리입니다. 같은 시스템을 기록한 네 곳 중 어느 두 곳이라도 내용이 다르면 빌드가 실패합니다. Badge의 `xl`을 잡아낸 게 바로 이 대조였습니다. 수정 내용은 v0.3.7 체인지로그에 평범한 버그 수정으로 들어갔습니다. 실제로 버그였으니까요. 문서 버그도 버그입니다. 앱을 멈추게 하지는 않지만, 대신 AI가 만드는 코드를 망칩니다.

(쓸데없이 시간을 잡아먹은 일도 하나 있었습니다. 리소스 주소를 처음에 `7onic://rules/core`로 지었더니 SDK가 요청마다 "Invalid URL"을 냈습니다. URL 스킴은 숫자로 시작할 수 없다는 걸 그때 알았습니다. 지금은 `design://7onic/`을 씁니다.)

## 41개도 맞고 42개도 맞았다

만드는 도중에 데이터 생성 과정이 컴포넌트가 41개라고 계속 우겼습니다. 공개 페이지, README, llms.txt 첫머리에는 전부 42개라고 적혀 있는데도요.

한동안 파일 열두 개 정도에 있는 42를 다 "고칠" 생각으로 꽤 찜찜하게 준비하다가, 고치기 전에 직접 하나하나 다시 세 보기로 했습니다. 결과는 둘 다 맞았습니다. 공개용 숫자는 사용자가 문서에서 보는 대로 차트 네 종류를 컴포넌트 4개로 세고, 내부 보조 컴포넌트 2개는 세지 않습니다. 기계가 세는 숫자는 하나로 합쳐진 Chart 소스와 그 보조 컴포넌트까지 셉니다. 같은 시스템을 다른 기준으로 센 것뿐이고, 각자 기준 안에서는 정확했습니다. 다음에 또 실수로 "고치지" 않도록 기준을 문서에 적어 두었습니다.

이 얘기를 하는 이유는 이번 주에 배운 것이 여기에 다 담겨 있기 때문입니다. 디자인 시스템을 기계로 검사할 때 어려운 건 검사기를 만드는 일이 아니었습니다. 내가 안다고 생각한 사실 중에 정확히 정의해 둔 게 생각보다 별로 없다는 걸 알게 되는 일이었습니다.

<br />

## 검사기도 틀렸다

공평하게 반대 경우도 적겠습니다. 스타일 덮어쓰기를 막는 규칙의 첫 버전은 `<DropdownMenuItem className="text-error">Delete</DropdownMenuItem>`을 위반으로 잡았습니다. 그런데 이건 제 문서에 실린 사용법입니다. 메뉴 항목에 시맨틱 글자색을 주는 게 삭제 같은 위험한 동작을 표시하는 정해진 방법입니다. 규칙이 지켜야 할 시스템보다 더 깐깐했던 겁니다.

그래서 이런 문제를 막는 관문을 하나 만들었습니다. 배포 전마다 검사기가 **llms.txt에 실린 검증된 예제 42개 전부에서 에러 0개, 경고 0개**를 내야 합니다. 문서가 검사기를 검증하고, 검사기가 문서를 검증합니다. 어느 한쪽이 무조건 옳다고 보지 않습니다.

여기에 더해 실제 MCP 통신(stdio)으로 처음부터 끝까지 돌려 보는 테스트도 있습니다. 가상의 작업 시나리오 5개를 준비하고, 시나리오마다 깨끗한 버전과 일부러 위반을 심은 버전을 만들었습니다. 현재 결과는 심어 둔 위반 15개 중 15개 검출, 깨끗한 버전에서 잘못 잡은 건 0개입니다. 배포 전마다 다시 돌리는데, 그래도 완전히 믿지는 않습니다. 그 정도로 믿는 게 맞다고 생각합니다.

<br />

## 설치 없이 쓸 수 있게

배포할 때 꼭 지키고 싶었던 조건이 하나 있었습니다. 사용자가 아무것도 설치하지 않고 이 기능을 다 쓸 수 있어야 한다는 것입니다. 그래서 서버를 빌드한 `dist/`를 레포에 커밋하고, 의존성 5개는 그 안에 함께 묶었습니다. Claude Code에서는 플러그인 명령 한 줄로 설치되고, 전체 용량은 3.3MB입니다.

여기에는 예전에 크게 데인 경험에서 나온 결정이 하나 있습니다. Claude Code 플러그인 최상위 폴더에 `package.json`이 있으면, 설치할 때 `npm ci`가 자동으로 돌아서 사용자마다 의존성을 통째로 내려받습니다. 같은 구조로 만든 예전 시제품이 그렇게 수백 MB까지 불어나는 걸 직접 봤습니다. 그래서 이 플러그인의 최상위 폴더에는 일부러 `package.json`을 두지 않았습니다. 실제 빌드 파일을 가리키는 심볼릭 링크만 있어서, 설치하거나 받아 올 게 없습니다.

<br />

## 지금까지의 결과

서버를 공개한 지 이틀밖에 안 돼서, 결론이라기보다는 첫인상 정도로 봐 주세요.

지금 확실히 말할 수 있는 건, 문서와 검사 장치가 서로 어긋나지 않고 점점 맞춰지고 있다는 점입니다. 이제 둘이 서로를 기준으로 만들어지고 검사되기 때문에, 문서가 낡으면 어딘가에서 빌드가 실패합니다. `llms.txt`가 쓸모없어진 게 아니라, 도구들이 정보를 가져가는 원본이 됐습니다. "이렇게 해 주세요"라는 부탁은 그대로 있고, 이제는 그걸 지키는지 지켜보는 장치가 생긴 겁니다.

아직 모르는 것도 있습니다. 다른 사람이, 다른 AI 에이전트로, 제 코드가 아닌 프로젝트에서 쓰면 어떻게 동작할지는 모릅니다. 검색어를 여러 언어로 받게 한 것(`그림자`로 그림자 토큰을, `チャット入力`으로 ChatInput을 찾는 기능)은 코드는 영어로 짜도 디자인은 자기 언어로 생각한다는 가정에서 만들었습니다. 그럴듯한 가정이지만, 실제 사용 데이터는 아직 하나도 없습니다.
