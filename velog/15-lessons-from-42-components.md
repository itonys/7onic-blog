# [API 회고] `<Card.Header>`의 점 하나 때문에 출시 18일 만에 전부 갈아엎은 이야기

안녕하세요, 디자인 시스템 [7onic](https://7onic.design)을 만들고 있는 개자이너입니다.

제 메모장 어딘가에 4월 4일, 그러니까 v0.1.0을 배포한 날 찍어 둔 스크린샷이 하나 있습니다. `<Card>` 안에 `<Card.Header>`, `<Card.Title>`, `<Card.Content>`가 가지런히 들어앉은 예제 코드였죠. 배포 버튼을 누르기 전에 그 JSX를 한참 들여다보면서 이런 생각을 했던 게 기억납니다.

*'오, 이거 진짜 디자인 시스템 같은데?'*

Radix도 이 모양이고, shadcn도 이 모양이니까요. 당연히 이 모양이어야 한다고 생각했습니다. 지금 돌아보면 저는 API를 *설계*한 게 아니라, 이미 머릿속에 박혀 있던 실루엣을 *따라 그리고* 있었습니다.

그리고 18일 뒤, 그걸 전부 지웠습니다.

"지원 중단(deprecated)" 같은 점잖은 단계도 없이 그냥 삭제였습니다. 공개 API에서 네임스페이스 25개가 사라졌고, 컴포넌트 파일 24개를 하루 오후 만에 다시 썼고, 문서 사이트의 `<Card.Header />`는 하나도 빠짐없이 `<CardHeader />`가 됐습니다. 4월 22일, v0.3.0은 하위 호환을 깨는 변경(Breaking Change)으로 나갔습니다. 이걸 버틸 수 있었던 건 앞으로 다시는 가질 수 없을 단 하나의 자원 덕분이었습니다. **프로덕션 사용자 0명.**

<br />

## 컴파운드 패턴이 "당연히 맞아" 보이던 날

3월 말, 첫 컴포넌트 38개의 뼈대를 잡을 때 이미 네임스페이스 패턴은 제 머릿속 템플릿에 구워져 있었습니다. 뭔가랑 비교해 보지도 않았습니다. Card에는 Header, Title, Content, Footer가 있고, Modal에는 Trigger, Content, Title, Description이 있죠. AlertDialog, Accordion, Tabs, Popover, Tooltip, Drawer… 전부 하위 부품이 서너 개에서 대여섯 개씩 있어서, 하나의 이름 아래 모여 살고 싶다고 아우성치는 것처럼 보였습니다.

그래서 제가 읽은 모든 튜토리얼이 하라는 대로 `Object.assign`으로 묶었습니다.

```ts
const Card = React.forwardRef<...>(...)
const CardHeader = React.forwardRef<...>(...)
const CardTitle = React.forwardRef<...>(...)
// ...

Object.assign(Card, { Header: CardHeader, Title: CardTitle, /* ... */ })

export { Card, CardHeader, CardTitle /* 혹시 모르니 이름으로도 내보냄 */ }
```

저 마지막 줄, *혹시 모르니 이름으로도 내보냄*. 결국 저를 살린 건 이 한 줄이었습니다. 왜 둘 다 남겨 뒀는지는 솔직히 기억이 안 납니다. 아마 확신이 없었고, "두 번씩 내보내기"가 싼 보험처럼 느껴졌던 것 같아요.

v0.1.0이 나갈 때 컴포넌트 38개 중 22개가 컴파운드 JSX를 쓰고 있었습니다. 네임스페이스는 총 25개. 문서 사이트도, 테스트 플레이그라운드도, GitHub 맨 위에 고정해 둔 README 예제도 전부 `<Card.Header />`였습니다. 제 눈에는 완성품으로 보였습니다.

<br />

## "당연히 맞다"의 진짜 의미

여기서 조심해서 말하고 싶은 게 있습니다. 교훈은 *"컴파운드 컴포넌트는 나쁘다"*가 아닙니다. Radix는 이 패턴으로 엄청난 덕을 보고 있고, 클라이언트 컴포넌트 안에서는 읽기도 정말 편합니다. 교훈은 그보다 좁고 더 민망합니다. **저는 API의 *모양*은 베꼈지만, 그 모양이 만들어진 *제약 조건*은 베끼지 않았습니다.**

Radix는 동작(behavior) 라이브러리입니다. 기본 부품 대부분이 처음부터 클라이언트 전용이죠. ref, 포털, 포커스 트랩, 이벤트 리스너에 붙어서 돌아가니까요. Radix 사용자가 리액트 서버 컴포넌트(RSC)에서 `<Dialog.Trigger />`를 렌더링하려는 상황 자체가 없습니다. 라이브러리의 존재 이유가 런타임 동작이니까요. 그러니 컴파운드 API가 그 이야기와 딱 맞습니다.

7onic은 동작 라이브러리가 아닙니다. *디자인* 시스템이죠. `<Card>`는 패딩과 테두리가 있는 div일 뿐이고, `<CardHeader>`는 아래 여백이 있는 div일 뿐입니다. 동작이 없어요. 이 컴포넌트들이 RSC 트리 안에서 못 돌아갈 이유가 하나도 없습니다. 제가 `Object.assign`으로 감싸지만 않았다면요. React Client Manifest는 이걸 서버와 클라이언트 경계 너머로 직렬화하지 못합니다. 어디서든 돌아갈 수 있었던 컴포넌트를, 점 하나와 맞바꿔서 조용히 클라이언트 전용으로 만들어 버린 겁니다.

4월 4일엔 몰랐습니다. 4월 22일에 알았죠. 누가 이슈를 올려 준 것도 아닙니다(다시 말하지만 사용자가 없었으니까요). 전혀 상관없는 걸 확인하려고 제 test-v4 플레이그라운드의 App Router 셸에 Card 하나를 넣는 순간, 플레이그라운드가 그대로 터지는 걸 보고 알았습니다.

<br />

## 결정

제가 가장 자주 곱씹는 부분이 여기입니다.

버그는 진짜였지만, 이론상 피해 범위는 아주 작았습니다. `<Card>`를 이름으로 직접 import해서 쓰는 사람은(기억하시죠? *혹시 모르니* 이름으로도 내보내고 있었습니다) 이 문제를 안 겪습니다. 망가진 건 컴파운드 JSX 경로뿐이었어요. 문서 사이트는 컴파운드 경로를 썼지만, 문서 사이트는 제 거니까 다시 쓰면 그만이었습니다. 합리적이고 차분한 사람이라면 마이그레이션 가이드를 쓰고, 0.x 동안은 두 API를 다 살려 두고, 실제 삭제는 Breaking Change가 "진짜로 의미 있는" 언젠가의 1.0으로 미뤘을 겁니다.

저는 그러지 않았습니다.

v0.2.9 RSC 패치를 배포한 바로 그날 오후에 v0.3.0 브랜치를 열고 네임스페이스를 전부 뜯어냈습니다. 네, 같은 날 버전 두 개입니다. 못 믿겠으면 체인지로그를 보세요. 그날 밤 쓴 ADR(아키텍처 결정 기록)에는 이유가 네 가지 적혀 있습니다. RSC 안전성, 트리 셰이킹이 죽은 코드 제거와 1:1로 맞아떨어지는 것, 새 하위 컴포넌트를 동기화하다 깜빡할 곳이 줄어드는 것, 그리고 AI 도구가 RSC 맥락에 `<Card.Header />`를 지어내서 터뜨리는 일이 없어지는 것. 전부 사실입니다. 하지만 이게 *6개월 뒤가 아니라 그날* 한 이유는 아닙니다.

그날 한 이유는 이겁니다. v0.1.0이 나온 지 18일. 그 18일 동안 제가 직접 관리하지 않는 프로젝트에서 이 패키지를 `npm install`한 사람은 정확히 0명이었습니다. Breaking Change의 비용이 0이었던 거죠. "작다"가 아니라 0. 그리고 이 코드베이스에 대해 앞으로 다시는 못 가질 선명함으로 알고 있었습니다. 이 숫자는 이제 올라가기만 한다는 걸요. 4월 22일에 내보내는 API가, 2년 뒤 제가 사과하고 다닐 API가 될 거라는 걸요.

**Breaking Change를 내기 좋은 때는 사용자가 0명일 때뿐입니다.** 저는 그 카드를 18일째에 썼습니다.

<br />

## 실제로 바뀐 것

diff 자체는 거의 지루했습니다. 코드베이스 전체에서 `<Card.Header />`가 `<CardHeader />`가 됐고, `Object.assign` 블록은 삭제됐고, *혹시 모르니* 남겨 뒀던 이름 내보내기가 공개 API의 전부가 됐습니다. 파일 24개, 문서 사이트 60페이지. 그리고 import 줄 351개를 하나하나 눈으로 확인했습니다. `Card.무언가`가 하나라도 남아 있지 않은지, 너무 많이 가져오거나 덜 가져온 곳은 없는지(최종 결과: 둘 다 0).

점 표기가 정말 좋았던 분들을 위해 ADR에는 "컴파운드 레시피" 25개를 같이 실었습니다. 자기 프로젝트에 넣으면 `<Card.Header />`를 로컬에서 되살릴 수 있는 작은 래퍼입니다. 단 하나의 조건이 있어요. 래퍼 파일 맨 위에 `'use client'`가 있어야 합니다. 이 조건이 이 이야기 전체를 지시어 한 줄로 압축한 셈입니다. 라이브러리는 점을 제공하지 않습니다. 점이 필요하면 무엇을 하는지 다 알고서, 클라이언트 전용이 되는 걸 스스로 선택하시면 됩니다.

<br />

## 남은 것

여기서 일반적인 교훈이 뭔지는 아직도 잘 모르겠고, 억지로 지어내고 싶지도 않습니다. 그 뒤 며칠 동안 알아챈 건 이겁니다. 저는 7onic 첫 버전을 디자인 시스템은 이렇게 만드는 거라고 *배운 대로* 만들었습니다. 그건 *이* 디자인 시스템에 필요한 방식으로 만든 것과 같은 게 아니었어요. 컴파운드 패턴은 제가 고른 게 아니라 물려받은 거였습니다. 그걸 뒤집은 게, 공개 API에 대해 처음으로 진짜 제 손으로 내린 결정이었습니다.

더 작지만 아마 더 쓸모 있는 것도 하나 있습니다. *혹시 모르니* 남겨 둔 이름 내보내기, 그때 누가 따졌다면 설명도 못 했을 그것이 마이그레이션 경로의 전부였습니다. 따로 쓸 마이그레이션이 없었어요. 새 API가 첫날부터 나란히 배포되고 있었으니까요. 저는 보험을 드는 줄도 모르고 보험을 들었고, 그 보험이 Breaking Change 값을 치렀습니다.

지금 컴포넌트 42개, 네임스페이스 0개. 첫 버전과 지금도 변호할 수 있는 버전 사이는 18일이었습니다.

그 뒤로는 Breaking Change를 한 번도 내지 않았습니다.
