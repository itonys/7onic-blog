# [API 회고] `<Card.Header>`의 점 하나 때문에 출시 18일 만에 API를 갈아엎었습니다

안녕하세요, 디자인 시스템 [7onic](https://7onic.design)을 만들고 있는 개자이너입니다.

v0.1.0을 배포한 4월 4일에 찍어 둔 스크린샷이 메모 어딘가에 남아 있습니다. `<Card>` 안에 `<Card.Header>`, `<Card.Title>`, `<Card.Content>`가 깔끔하게 들어간 예제 코드입니다. 배포 버튼을 누르기 전에 이 코드를 한참 보면서 '오, 이제 좀 디자인 시스템 같네' 하고 뿌듯해했던 기억이 납니다.

Radix도 이렇게 쓰고 shadcn도 이렇게 쓰니까, 당연히 이게 맞다고 생각했습니다. 지금 보면 API를 설계했다기보다는 익숙한 모양을 그대로 따라 한 거였습니다.

그리고 18일 뒤에 이걸 전부 지웠습니다.

지원 중단(deprecated) 예고 같은 단계도 없이 바로 삭제했습니다. 공개 API에서 네임스페이스 25개를 없앴고, 컴포넌트 파일 24개를 오후 한나절 만에 다시 썼고, 문서 사이트의 `<Card.Header />`를 하나도 빠짐없이 `<CardHeader />`로 바꿨습니다. 4월 22일에 v0.3.0을 하위 호환이 깨지는 변경(Breaking Change)으로 배포했습니다. 이게 가능했던 이유는 딱 하나, 그때가 아니면 다시 오지 않을 조건이었습니다. **실제로 쓰는 사용자가 0명이었습니다.**

<br />

## 컴파운드 패턴이 당연해 보였던 이유

3월 말에 첫 컴포넌트 38개의 뼈대를 만들 때, 네임스페이스 패턴은 이미 머릿속에 기본값으로 박혀 있었습니다. 다른 방식과 비교해 보지도 않았습니다. Card에는 Header, Title, Content, Footer가 있고, Modal에는 Trigger, Content, Title, Description이 있습니다. AlertDialog, Accordion, Tabs, Popover, Tooltip, Drawer도 하위 부품이 3~6개씩 있어서, 하나의 이름 아래 묶는 게 자연스러워 보였습니다.

그래서 튜토리얼에서 늘 보던 대로 `Object.assign`으로 묶었습니다.

```ts
const Card = React.forwardRef<...>(...)
const CardHeader = React.forwardRef<...>(...)
const CardTitle = React.forwardRef<...>(...)
// ...

Object.assign(Card, { Header: CardHeader, Title: CardTitle, /* ... */ })

export { Card, CardHeader, CardTitle /* 혹시 몰라서 이름으로도 내보냄 */ }
```

마지막 줄의 "혹시 몰라서 이름으로도 내보냄", 나중에 저를 살린 게 바로 이 한 줄입니다. 왜 두 방식을 다 남겼는지는 기억이 안 납니다. 확신이 없어서 일단 둘 다 내보내 두면 손해 볼 일은 없겠다 싶었던 것 같습니다.

v0.1.0을 배포할 때 컴포넌트 38개 중 22개가 이 점 표기(컴파운드 JSX)를 쓰고 있었고, 네임스페이스는 모두 25개였습니다. 문서 사이트, 테스트 플레이그라운드, GitHub 맨 위에 걸어 둔 README 예제까지 전부 `<Card.Header />`였습니다. 제 눈에는 완성된 걸로 보였습니다.

<br />

## 제가 놓친 것

오해가 없게 먼저 말하면, "컴파운드 컴포넌트는 나쁘다"는 얘기가 아닙니다. Radix는 이 패턴 덕을 많이 보고 있고, 클라이언트 컴포넌트 안에서는 읽기도 확실히 편합니다. 제 실수는 좀 더 좁고, 그래서 더 부끄럽습니다. **API 모양은 따라 했는데, 그 모양이 나온 배경과 제약은 따져 보지 않았습니다.**

Radix는 동작(behavior)을 담당하는 라이브러리입니다. 부품 대부분이 ref, 포털, 포커스 트랩, 이벤트 리스너를 쓰기 때문에 처음부터 클라이언트에서만 돌아갑니다. Radix를 쓰는 사람이 서버 컴포넌트(RSC)에서 `<Dialog.Trigger />`를 렌더링할 일은 애초에 없습니다. 런타임 동작이 라이브러리의 핵심이니, 컴파운드 API와 잘 맞습니다.

[7onic](https://7onic.design)은 동작 라이브러리가 아니라 디자인 시스템입니다. `<Card>`는 패딩과 테두리가 있는 div이고, `<CardHeader>`는 아래 여백이 있는 div일 뿐입니다. 동작이 없으니 서버 컴포넌트에서 못 쓸 이유도 없습니다. 그런데 제가 `Object.assign`으로 묶어 버렸고, React의 Client Manifest는 이렇게 붙인 속성을 서버와 클라이언트 경계 너머로 넘기지 못합니다. 어디서나 쓸 수 있었던 컴포넌트를, 점 하나 쓰자고 클라이언트 전용으로 만들어 버린 겁니다.

4월 4일에는 이걸 몰랐고, 4월 22일에야 알았습니다. 누가 이슈를 올려 준 것도 아닙니다(사용자가 없었으니까요). 전혀 다른 걸 확인하려고 테스트용 플레이그라운드(test-v4)의 App Router 화면에 Card를 하나 넣었는데, 그 순간 화면이 통째로 깨졌습니다.

<br />

## 바로 지우기로 했다

이 글에서 가장 오래 고민했던 부분입니다.

버그는 확실했지만, 따지고 보면 영향 범위는 작았습니다. `<Card>`를 이름으로 import해서 쓰면(앞에서 말한 "혹시 몰라서" 덕분에 이 방식도 이미 있었습니다) 문제가 생기지 않습니다. 깨지는 건 점 표기뿐이었고, 점 표기를 쓰는 문서 사이트는 제가 관리하니 고치면 그만이었습니다. 신중한 사람이라면 마이그레이션 가이드를 쓰고, 0.x 동안은 두 방식을 같이 유지하고, 실제 삭제는 1.0 무렵으로 미뤘을 겁니다.

저는 그렇게 하지 않았습니다.

v0.2.9 RSC 패치를 배포한 그날 오후에 바로 v0.3.0 브랜치를 만들고 네임스페이스를 전부 걷어 냈습니다. 하루에 버전 두 개를 낸 셈인데, 체인지로그에 그대로 남아 있습니다. 그날 밤 쓴 ADR(아키텍처 결정 기록)에는 이유를 네 가지 적었습니다.

- 서버 컴포넌트에서 안전하게 쓸 수 있다
- 안 쓰는 코드가 트리 셰이킹으로 깔끔하게 빠진다
- 하위 컴포넌트를 추가할 때 같이 챙겨야 할 곳이 줄어든다
- AI 도구가 서버 컴포넌트에 `<Card.Header />`를 써서 화면을 깨뜨리는 일이 없어진다

전부 맞는 이유입니다. 하지만 6개월 뒤가 아니라 바로 그날 지운 이유는 따로 있습니다.

v0.1.0을 낸 지 18일이 지났는데, 그동안 제가 관리하지 않는 프로젝트에서 이 패키지를 설치한 사람은 0명이었습니다. Breaking Change의 비용이 "적은" 게 아니라 정말로 0이었습니다. 그리고 이 숫자는 앞으로 늘어나기만 한다는 것도 분명했습니다. 4월 22일에 내보내는 API가 2년 뒤에도 제가 책임져야 할 API였습니다.

**Breaking Change를 마음 편히 낼 수 있는 건 사용자가 0명일 때뿐입니다.** 저는 그 기회를 출시 18일째에 썼습니다.

<br />

## 실제로 바꾼 것

바꾼 내용 자체는 단순했습니다. 코드 전체에서 `<Card.Header />`를 `<CardHeader />`로 바꾸고, `Object.assign` 부분을 지웠습니다. "혹시 몰라서" 남겨 둔 이름 내보내기가 그대로 공개 API가 됐습니다. 파일 24개와 문서 사이트 60페이지를 고쳤고, import 줄 351개를 하나하나 직접 확인했습니다. `Card.뭐시기`가 남은 곳은 없는지, 필요 없는 걸 가져오거나 필요한 걸 빠뜨린 곳은 없는지 봤고, 결과는 둘 다 0건이었습니다.

점 표기가 마음에 들었던 분들을 위해 ADR에 "컴파운드 레시피" 25개도 넣었습니다. 자기 프로젝트에 넣기만 하면 `<Card.Header />`를 다시 쓸 수 있게 해 주는 작은 래퍼입니다. 조건은 하나, 래퍼 파일 맨 위에 `'use client'`를 붙여야 합니다. 사실 이 조건 하나에 이번 이야기가 다 들어 있습니다. 라이브러리는 점 표기를 기본으로 주지 않고, 꼭 쓰고 싶다면 클라이언트 전용이 된다는 걸 알고 직접 선택하면 됩니다.

<br />

## 남은 생각

여기서 그럴듯한 교훈을 끌어내고 싶지는 않습니다. 다만 그 뒤 며칠 동안 깨달은 게 하나 있습니다. 저는 7onic 첫 버전을 "디자인 시스템은 원래 이렇게 만든다"고 배운 대로 만들었고, 그건 7onic에 맞는 방식과는 달랐습니다. 컴파운드 패턴은 제가 고른 게 아니라 그냥 따라온 것이었습니다. 그걸 뒤집은 게 공개 API에 대해 처음으로 제가 직접 내린 결정이었습니다.

조금 더 실용적인 깨달음도 있습니다. 당시에는 누가 물어봤으면 이유도 못 댔을 "혹시 몰라서" 이름 내보내기가, 결국 마이그레이션 경로의 전부였습니다. 새 API가 첫날부터 같이 배포되고 있었으니 따로 마이그레이션 방법을 만들 필요가 없었습니다. 보험인 줄도 모르고 들어 둔 보험이 Breaking Change 비용을 대신 내 준 셈입니다.

지금은 컴포넌트 42개, 네임스페이스 0개, 사용자 `node_modules`에 깔리는 의존성 6개입니다. 첫 버전에서 지금도 자신 있게 내놓을 수 있는 버전까지 18일이 걸렸습니다.

그 뒤로는 Breaking Change를 한 번도 내지 않았습니다.
