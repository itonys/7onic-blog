# [회고] 일부러 골라야 쓰는 도구는 결국 안 쓰인다

안녕하세요, 디자인 시스템 [7onic](https://7onic.design)을 만들고 있는 개자이너입니다.

다섯 번째 버전은 설정까지 알아서 해 주는 버전이었습니다. 팀에 한 말도 딱 한 문장이었습니다. "MCP 서버만 추가해 주세요. 나머지는 제가 다 해 둘게요." 토큰, 컴포넌트, 사용 규칙까지 전부 연결해 둔 상태였습니다.

그래도 대부분 추가하지 않았습니다.

그때부터 고민의 방향이 바뀌었습니다. "어떻게 하면 더 쓰기 편해질까?"가 아니라, 훨씬 껄끄러운 질문이었습니다. "애초에 사람들이 이걸 왜 골라서 써야 하지?"

<br />

## 문을 다섯 번 만들었다

7onic 얘기가 아니라 예전에 함께 일하던 팀에서 있었던 일입니다. 자세한 사정보다는 반복된 패턴이 더 쓸 만한 이야기라서, 패턴 위주로 적겠습니다.

처음에는 디자인 파일이었습니다. 컴포넌트와 variant까지 제대로 갖춘 파일이었고, 공개만 해 두면 다들 찾아서 쓸 줄 알았습니다. 아무도 안 오길래 파일이 문제라고 생각했습니다. 실제로 일하는 곳과 너무 멀다고요. 그래서 언제 무엇을 쓰면 되는지 설명하는 가이드 사이트를 만들었습니다.

사이트도 아무도 안 읽었습니다.

다음은 npm 패키지였습니다. 이때가 제일 자신 있었습니다. 이제 문서로 권하는 게 아니라, 엔지니어들이 매일 쓰는 코드 환경에 바로 들어가는 진짜 코드였으니까요. 설치 한 번, import 한 번이면 버튼이 나왔습니다.

그 무렵에는 UI 코드를 이미 AI가 꽤 많이 쓰고 있었습니다. 그래서 이런 생각이 들었습니다. 사람이 규칙을 안 읽는다면 AI는 읽지 않을까? 그래서 `llms.txt`를 썼고, 그다음에 만든 게 맨 처음 말한 설정 자동화 MCP 서버입니다.

버전을 낼 때마다 안 쓸 이유를 하나씩 없앴습니다. 그런데도 어느 버전도 쓰이지 않았습니다.

<br />

## 알아채기까지 오래 걸렸다

이걸 깨닫기까지 꽤 오래 걸렸습니다. 조금 부끄럽지만 그대로 적겠습니다.

실패할 때마다 저는 전달 방식에서 원인을 찾았습니다. 파일은 코드와 너무 멀었다, 그래서 웹사이트로 옮겼더니 이번에는 에디터와 너무 멀었다, 패키지는 설정이 번거로웠다. (지금 보면 AI용 문서도 누군가 AI에게 "이거 읽어"라고 알려 줘야 했으니, 결국 같은 문제였습니다.) 게다가 그 원인들이 하나같이 실제로 맞는 말이었습니다. 그래서 멈추기가 더 어려웠습니다. 전달 방식을 고치고, 새 문을 내놓고, 또 기다렸습니다.

다섯 번째 문을 만들고 나서야 알았습니다. 저는 문 만드는 실력만 늘었고, 정작 그 문으로 다니는 사람은 없었다는 걸요. 사람들은 원래 하던 방식대로 일했습니다. 에디터를 열고, AI에게 묻고, 기능을 배포합니다. 그 흐름 옆에서 기다리는 디자인 시스템은 아무리 잘 만들어도 돌아가는 길일 뿐입니다. 그리고 선택 사항 하나 때문에 일부러 돌아가는 사람은 없습니다.

결국 남은 결론은 한 줄이었습니다.

**일부러 골라야 쓰는 도구는 결국 안 쓰인다.**

옆에서 얌전히 기다리기만 하는 규칙은 규칙이라고 하기 어렵습니다. 문서가 유난히 잘 정리된 권장 사항에 가깝습니다.

<br />

## 그런데 7onic도 똑같았다

7onic은 이 일을 다 겪은 뒤에 만들었습니다. 드디어 그 패턴을 깬 버전이라고 말하고 싶지만, 그렇게 간단하지는 않습니다. 7onic의 구성을 보면 Figma 호환 JSON에 담긴 디자인 토큰, 문서 사이트, npm 패키지, `llms.txt`, MCP 서버입니다. 결국 같은 문 다섯 개를 다시 만든 셈입니다.

달라진 점은 가장 비싸게 배운 교훈 두 가지를 어떻게 적용했느냐입니다.

<br />

## 교훈 1: 사람들은 설정 단계에서 포기한다

npm 패키지 때 배운 교훈입니다. 사람들이 싫어한 건 디자인 시스템 자체가 아니었습니다. 첫 버튼을 띄우기 전까지 해야 하는 설정 작업이 싫었던 겁니다. 그래서 7onic에서는 설정 방법을 더 친절하게 설명하는 대신, 설정 자체를 없애는 쪽으로 갔습니다.

AI 쪽 설정은 명령 한 줄이면 끝납니다.

```bash
claude plugin marketplace add itonys/7onic && claude plugin install 7onic-design@7onic
```

CLI로 시작하는 경우에는 `npx 7onic init`이 7onic 스킬과 디자인 에이전트를 프로젝트의 `.claude/` 폴더에 바로 넣어 줍니다(2026-10-09 CLI 0.1.16에서 추가). 묻지 않고 바로 넣는 `--claude` 플래그도 있습니다.

다만 기본 동작은 먼저 물어보는 것이고, 기본 선택은 "아니요"입니다. `init`의 다른 질문을 전부 "예"로 넘기는 `--yes`를 써도 이 질문만은 건너뛰지 않습니다. 급하게 명령을 쳤다는 이유만으로 디자인 시스템이 남의 `.claude/` 폴더에 몰래 파일을 넣는 건 싫었습니다.

<br />

## 교훈 2: 규칙은 아무도 안 읽는다, 그러니 작업하는 자리에 둔다

저는 이쪽이 더 중요하다고 생각합니다.

가이드 사이트는 누군가 열어 주기를 기다렸고, `llms.txt`는 누군가 AI에게 읽으라고 알려 주기를 기다렸습니다. 둘 다 작업 흐름 밖에 놓인 규칙이었습니다. 7onic에서는 MCP 서버가 연결되는 순간, AI가 코드를 한 줄도 쓰기 전에 규칙을 넘겨줍니다. 그중 하나는 권장이 아니라 지시입니다.

```text
ALWAYS validate_code on the generated TSX before returning it;
fix every error and re-validate.
```

(생성한 TSX를 넘기기 전에 반드시 validate_code로 검사하고, 에러를 모두 고친 뒤 다시 검사할 것)

`validate_code`는 생성된 TSX를 분석해서 규칙 14개로 검사합니다. 그중 9개는 에러입니다. 색을 하드코딩했거나, 임의 값을 넣었거나, 컴포넌트가 있는데 HTML 요소를 그대로 쓴 경우 같은 것들입니다. 사람이 이 검사를 챙길 필요가 없습니다. AI가 자기가 만든 코드를 직접 검사하고, 에러가 나오면 사람이 화면을 보기 전에 고칩니다.

앞의 문 다섯 개와 진짜 다른 점이 여기입니다. 그 다섯 개는 전부 누군가 직접 찾아가서 봐야 했습니다. 이 검사는 누가 챙기든 말든 알아서 돌아갑니다.

(물론 완벽하지는 않습니다. AI가 "이 규칙은 여기엔 해당 안 된다"고 판단해 버릴 수도 있고, 검사기는 미리 정해 둔 것만 잡아냅니다. 규칙을 전부 통과해도 화면 자체는 그저 그럴 수 있습니다. 이건 또 다른 문제라 다음에 따로 쓰겠습니다.)

<br />

## 이걸로 충분할까

아직은 모르겠습니다.

두 교훈 모두 7onic이 프로젝트에 들어간 다음에야 효과가 있습니다. 일단 들어가면 규칙은 문서 탭에서 기다리지 않고 AI와 함께 움직이고, 설정도 핑계가 안 될 만큼 짧습니다. 하지만 처음에 프로젝트에 넣을지 말지는 여전히 누군가가 정해야 하고, 그 부분은 제가 뭘 더 만든다고 해결되지 않습니다.

어쩌면 그게 오픈소스 디자인 시스템이 할 수 있는 한계일지도 모릅니다. 7onic을 쓰는 쪽이 안 쓰는 쪽보다 편하게 만들 수는 있습니다. 한번 쓰기 시작하면 규칙에서 벗어나기 어렵게 만들 수도 있습니다. 하지만 7onic이 유일한 선택지가 되느냐는 라이브러리가 정할 수 있는 일이 아닙니다. 도입하는 쪽이 정할 일입니다.

적어도 이제는 여섯 번째 문을 만들어 놓고 "이번엔 해결했다"고 말하지는 않습니다.
