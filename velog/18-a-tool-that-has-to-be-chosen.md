# [회고] 골라야 쓰는 도구는 선택받지 못한다

안녕하세요, 디자인 시스템 [7onic](https://7onic.design)을 만들고 있는 개자이너입니다.

다섯 번째 버전은 설정까지 알아서 했습니다. 팀에 건넨 말은 거의 한 문장이었어요. "MCP 서버만 넣어 주세요, 나머지는 제가 알아서 할게요." 토큰도, 컴포넌트도, 쓰는 규칙도 전부 연결해 둘 테니까.

대부분 넣지 않았습니다.

그때부터 질문이 바뀌었습니다. "어떻게 하면 더 쓰기 쉬워질까"가 아니라, 훨씬 불편한 질문으로요. *애초에 누가 이걸 왜 골라서 쓰겠는가?*

<br />

## 다섯 개의 문

7onic이 아니라, 함께 일했던 팀에서 있었던 일입니다. 세부 사항은 별로 중요하지 않아요. 솔직히 구체적인 사정보다 패턴이 더 쓸모 있습니다.

시작은 디자인 파일이었습니다. 컴포넌트, 배리언트, 갖출 건 다 갖춘. 공개해 두면 사람들이 찾아올 줄 알았어요. 오지 않자 저는 파일이 문제라고 판단했고(실제로 일하는 곳에서 너무 멀다고요), 언제 무엇을 쓰는지 설명하는 가이드 사이트를 만들었습니다.

사이트도 아무도 읽지 않았습니다.

그래서 npm 패키지로 냈습니다. 솔직히 가장 믿었던 버전입니다. 더는 조언이 아니었거든요. 엔지니어들이 원래 사는 세계 안에 들어간 코드였고, 설치 한 번과 import 한 번이면 버튼이 나왔습니다.

그 무렵엔 어차피 UI의 상당 부분을 AI가 쓰고 있었고, 그게 새 아이디어를 줬습니다. 사람이 규칙을 안 읽는다면, 모델은 읽지 않을까? 그래서 `llms.txt`를 썼습니다. 그다음이 설정을 자동으로 해 주는 MCP 서버, 맨 처음에 나온 그것입니다.

버전마다 쓰지 않을 이유를 하나씩 없앴습니다. 그런데 어느 것도 쓰이지 않았습니다.

<br />

## 제가 느렸던 부분

이걸 깨닫기까지 얼마나 걸렸는지는 솔직하게 말해야겠습니다. 조금 창피하니까요.

버전이 실패할 때마다 저는 포장 탓을 찾았습니다. 파일은 코드에서 너무 멀었다. 좋아, 그래서 다음 건 웹사이트에 올렸는데, 그건 에디터에서 너무 멀었다. 패키지는 설정이 필요했다. (돌이켜 보면 AI 문서는 누군가 AI에게 그걸 가리켜 줘야 했는데, 같은 문제가 모자만 바꿔 쓴 셈이었죠.) 그리고 그 설명들이 하나같이 *사실*이었습니다. 그래서 멈추기가 어려웠어요. 포장을 고치고, 다음 문을 내놓고, 기다렸습니다.

문을 다섯 개 만들고 나서야 알아챘습니다. 저는 문을 아주 잘 만드는 사람이 되어 있었고, 누구의 길도 그 문들을 지나가지 않았다는 걸요. 사람들은 원래 다니던 길로 움직였습니다. 에디터를 열고, AI에게 묻고, 기능을 내보내고. 그 길 옆에서 기다리는 디자인 시스템은 아무리 잘 만들어도 우회로입니다. 그리고 사람들은 선택지 하나 때문에 돌아가지 않아요.

남은 문장은 짧았습니다.

**골라야 쓰는 도구는 선택받지 못한다.**

옆에서 얌전히 기다리는 규칙은 사실 규칙이 아닙니다. 문서가 유난히 잘 되어 있는 제안일 뿐이죠.

<br />

## 그리고 7onic을 봤다

7onic은 그 모든 일 다음에 나왔습니다. 마침내 그 패턴을 깬 버전이라고 말하고 싶지만, 그렇게 간단하지는 않습니다. 7onic이 무엇인지 보면 이렇거든요. Figma 호환 JSON 파일에 담긴 디자인 토큰, 문서 사이트, npm 패키지, `llms.txt`, MCP 서버. 똑같은 다섯 개의 문을 다시 만든 겁니다.

달라진 건, 가장 비싸게 배운 두 가지 교훈을 어떻게 썼느냐입니다.

<br />

## 교훈 하나: 사람들은 설정에서 포기한다

이건 npm 패키지에서 배웠습니다. 사람들은 디자인 시스템을 거부한 게 아니었어요. 설정을 거부했습니다. 첫 버튼이 나오기 전에 해야 하는 연결 작업 전부를요. 그래서 7onic에서는 그 연결 작업을 더 잘 설명하는 대신 아예 없애려고 했습니다.

AI 쪽은 전부 명령 한 줄입니다.

```bash
claude plugin marketplace add itonys/7onic && claude plugin install 7onic-design@7onic
```

CLI에서 시작한다면, `npx 7onic init`이 7onic 스킬과 디자인 에이전트를 프로젝트의 `.claude/` 폴더에 바로 넣어 줄 수 있습니다(2026-10-09 CLI 0.1.16에서 추가). 묻지 않고 설치하는 `--claude` 플래그도 있고요.

그래도 기본으로는 묻고, 기본 답은 "아니요"입니다. `init`의 다른 질문을 모두 수락하는 `--yes`도 이것만은 건너뜁니다. 급하다는 이유로 디자인 시스템이 남의 `.claude/` 폴더에 조용히 파일을 쓰는 건 원하지 않았거든요.

<br />

## 교훈 둘: 아무도 규칙을 읽지 않는다, 그러니 일이 일어나는 곳에 둔다

제가 더 중요하게 여기는 쪽은 이겁니다.

가이드 사이트는 사람이 열어 주기를 기다렸습니다. `llms.txt`는 누군가 AI에게 그걸 가리켜 주기를 기다렸고요. 둘 다 작업 *옆*에 놓인 규칙이었습니다. 7onic에서는 MCP 서버가 연결되는 순간, AI가 한 줄도 쓰기 전에 규칙을 건넵니다. 그중 하나는 제안의 말투가 아닙니다.

```text
ALWAYS validate_code on the generated TSX before returning it;
fix every error and re-validate.
```

(생성한 TSX를 돌려주기 전에 항상 validate_code를 실행하고, 모든 에러를 고친 뒤 다시 검사할 것)

`validate_code`는 생성된 TSX를 분석해서 규칙 14개로 검사합니다. 그중 9개는 에러예요(하드코딩된 색, 임의 값, 컴포넌트가 있는데 쓴 네이티브 요소 같은 것들). 누구도 이걸 돌리는 걸 기억할 필요가 없습니다. AI가 자기 결과물에 직접 돌리고, 에러를 보고, 사람이 화면을 보기 전에 고칩니다.

그게 다섯 개의 문과의 진짜 차이입니다. 다섯 개 모두, 누군가 직접 가서 보기로 마음먹어야 했어요. 이건 누가 기억하든 말든 돌아갑니다.

(완벽하진 않습니다. AI는 여전히 어떤 규칙이 해당되지 않는다고 판단할 수 있고, 검사기는 잡도록 쓰인 것만 잡습니다. 모든 규칙을 통과하고도 그저 그런 화면일 수 있어요. 그건 다른 문제고, 아마 다른 글이 될 겁니다.)

<br />

## 그걸로 충분할까?

아직 모르겠습니다.

두 교훈 모두 7onic이 프로젝트에 들어온 *뒤*에 작동합니다. 일단 들어오면 규칙은 문서 탭에서 기다리지 않고 AI와 함께 움직이고, 설정은 더 이상 핑계가 되지 못할 만큼 짧습니다. 하지만 애초에 프로젝트에 들여오는 건 여전히 누군가의 선택이고, 그 부분은 제가 만들어서 해결할 수 있는 게 아닙니다.

어쩌면 그게 오픈소스 디자인 시스템의 정직한 경계일지도 모르겠습니다. 7onic을 지나는 길을 돌아가는 길보다 짧게 만들 수는 있습니다. 일단 그 길에 들어서면 벗어나기 어렵게 만들 수도 있고요. 하지만 그게 *유일한* 길이 되느냐는 라이브러리가 정할 일이 아닙니다. 그건 받아들이는 쪽의 몫이죠.

제가 그만둔 건, 여섯 번째 문을 만들어 놓고 해결책이라고 부르는 일입니다.
