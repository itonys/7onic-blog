# [배포 회고] 내 패키지가 없다는 npm, 네 번의 실패, 그리고 토큰 0개

안녕하세요, 디자인 시스템 [7onic](https://7onic.design)을 만들고 있는 개자이너입니다.

10월 7일, `@7onic-ui/tokens@0.3.7`을 배포하려는데 npm이 제 패키지가 존재하지 않는다고 했습니다.

```
npm error 404 Not Found - PUT https://registry.npmjs.org/@7onic-ui%2ftokens
npm error 404  '@7onic-ui/tokens@0.3.7' is not in this registry.
```

404입니다. PUT 요청에서요. 같은 워크플로로 이미 열 번도 넘게 배포한 패키지인데요. 릴리스 자체는 더 준비될 수 없을 만큼 준비돼 있었습니다. 세 가지 환경 스모크 테스트 통과, 배포 전 검사 17개 통과, 체인지로그 확정. 남은 건 버튼 하나였어요. 그날 그 버튼을 네 번 눌렀고, npm은 네 번 거절했습니다. 매번 다른 에러로요.

다음 날이 끝날 무렵 배포는 고쳐졌습니다. 더 좋은 토큰을 만들어서가 아니라, **제가 가진 npm 토큰을 전부 지우고 GitHub의 `NPM_TOKEN` 시크릿까지 통째로 없애서**요. 지금 레포 시크릿은 0개이고, 배포는 그 어느 때보다 잘 됩니다.

실패 네 번을 차례로 풀어 보겠습니다. 하나같이 배우고 싶지 않았던 걸 가르쳐 줬거든요.

<br />

## 실패 1: 사실은 401이었던 404

아무도 안 알려 주는 첫 번째. **npm은 배포 시 인증 실패를 404로 보고합니다.** 401도 403도 아니고, 그냥 "이 레지스트리에 그런 패키지 없음". 꼭 제 패키지 이름을 오타 낸 것처럼 읽힙니다. 이유 자체는 타당해요(권한 없는 사람에게 패키지가 있는지 없는지 알려 주지 않으려는 거죠). 하지만 *내* 패키지에 *내* CI라면, 누가 봐도 맞는 URL을 20분 동안 노려보게 됩니다.

진짜 원인은 처음부터 GitHub 시크릿 화면에 있었습니다. `NPM_TOKEN`, 마지막 수정일 4월 9일. 세분화된(granular) npm 토큰은 만료가 됩니다. 제 토큰은 그 뒤 다섯 달 사이 어느 날 조용히 죽어 있었고, 4월 이후로 아무것도 배포하지 않았으니 아무것도 눈치채지 못했던 거죠. 만료일에 시끄럽게 실패한 게 아니라, 그냥 저를 기다리고 있었습니다.

<br />

## 실패 2, 3: 전부 제 잘못

민망한 부분이니 한 번에 털어놓겠습니다.

새 토큰을 만들어서 `gh secret set NPM_TOKEN`으로 등록했습니다. 진짜 터미널이 아니라 AI 에이전트 세션 안에서 한 줄로 입력했어요. 한 줄 입력은 대화형이 아니고, 대화형이 아니면 붙여넣기 프롬프트가 안 뜨고, 프롬프트가 안 뜨면 명령은 신나게 *빈 문자열*을 배포 자격 증명으로 저장합니다. 다음 실행은 `ENEEDAUTH`로 실패했고, 워크플로 환경 변수 목록에는 토큰이 아예 없었습니다. 모든 사람으로부터 패키지를 지켜 냈습니다. 저 자신까지 포함해서요.

세 번째 시도는 나아졌습니다. 그러니까 더 나빠졌다는 뜻입니다. 이번엔 클립보드를 그대로 시크릿에 넣었는데, 클립보드에 토큰 *이름과 값이 붙은 채로* 들어 있었습니다. npm 화면에서 드래그 한 번에 둘 다 선택됐거든요. 그래서 GitHub는 `7onic-gha-publish-2026-10npm_...` 같은 걸 충실하게 시크릿으로 저장했고, 워크플로는 그걸 그대로 넘겼고, npm은 아주 합리적으로 그게 뭔지 몰랐습니다. 또 404.

결국 실마리를 준 건 토큰 상세 페이지의 한 줄이었습니다. **"Last used: never."** 워크플로 로그에는 환경 변수가 설정되고 배포를 시도한 기록이 있는데, npm은 그 토큰을 한 번도 본 적이 없다는 거예요. 이건 권한 문제가 아니라, 봉투에 엉뚱한 바이트가 들어 있는 문제였습니다.

(이런 종류의 문제 해결법을 기록해 두자면: 뭔가 등록하기 전에 `pbpaste | head -c 4`. `npm_`이 안 나오면 멈추세요.)

<br />

## 실패 4: npm이 속마음을 말하다

드디어 값이 맞게 들어가자, 네 번째 시도는 완전히 새로운 에러를 냈습니다. 이번엔 설명이 붙은 403이었어요.

> Two-factor authentication or granular access token with bypass 2fa enabled is required to publish packages.

새 토큰에는 예전 토큰에 있던 체크박스 하나가 빠져 있었습니다. "2단계 인증 우회(bypass 2FA)". 좋아, 체크하고 다시 만들면 되지. 그때부터 npm이 저에게 직접 말을 걸기 시작했습니다. 토큰 생성 화면에 2FA 우회 + 직접 배포 권한 토큰은 **2027년 1월부터 동작하지 않는다**는 경고가 떠 있었고, 체크박스를 누르자 두 번째 경고가 떴습니다. "이 옵션에는 보안 위험이 있습니다. 자동화나 CI/CD에는 Trusted Publishing을 쓰세요."

하루 만의 전체 그림은 이랬습니다. 제 토큰 경로는 서로 관계없는 네 가지 이유로 네 번 실패했고, 플랫폼은 빨간 글씨로 두 번이나 이 방식 전체가 석 달 남았다고 말하고 있었습니다.

Trusted Publishing은 "언젠가 옮길 것" 목록에 있었는데, 그 "언젠가"가 끝났습니다.

<br />

## 전환은 실패 3번보다 짧게 걸렸다

솔직히 이 사건 전체에서 가장 김빠지는 부분입니다.

Trusted Publishing(프로토콜 이름으로는 OIDC)은 공유 시크릿 방식 대신, npm이 GitHub에게 직접 묻는 방식입니다. *이 배포가 정말 이 레포의 이 워크플로에서 왔어?* GitHub는 실행마다 신원 증명에 서명하고, npm은 그걸 확인합니다. 만료될 토큰도, 붙여넣을 시크릿도, 샐 것도 없어요. npm 쪽에서는 패키지마다 한 번씩 배포자를 등록하면 됩니다. 칸은 네 개, 소유자·레포·워크플로 파일 이름·환경. 패키지가 셋이라 세 번 했습니다.

워크플로 쪽 변경은 거의 삭제입니다. 모든 배포 단계에서 `NODE_AUTH_TOKEN` 환경 변수를 지웁니다. 이게 중요해요. 토큰이 남아 있으면 OIDC보다 우선 적용돼서 업그레이드 전체가 조용히 무효가 됩니다. 그리고 진짜 함정이 하나 있었습니다. Trusted Publishing은 **npm 11.5.1 이상**이 필요한데, Node 20 러너에는 npm 10이 들어 있습니다. 처음엔 `npm install -g npm@latest`를 넣으려다가, 커밋 전에 확인해 봤는데 정말 다행이었습니다. 지금 `npm@latest`는 12.2.0이고, engines 필드가 Node 22 이상을 요구합니다. 제 러너에서는 설치부터 실패했을 거예요. 그래서 11번대로 고정했습니다.

```yaml
- name: Upgrade npm for trusted publishing
  run: npm install -g npm@11 && npm --version
```

마이그레이션은 이게 전부입니다. 등록 세 번, 환경 변수 삭제 세 번, 버전 고정한 업그레이드 단계 하나.

<br />

## 드디어 초록불

10월 8일. 세 작업이 모두 통과했습니다. tokens 18초, CLI 16초, react는 4분이 조금 안 됐어요. 그리고 배포마다 토큰 시절엔 한 번도 없던 게 따라왔습니다. 워크플로 신원으로 서명되고 Sigstore 공개 투명성 로그에 기록된 출처 증명(provenance)입니다. 이제 누구든 `@7onic-ui/react@0.3.7`이 정확히 그 커밋에서, 정확히 그 GitHub Actions 실행으로 빌드됐다는 걸 확인할 수 있습니다. README에 몇 달째 "공급망 검증됨"이라고 써 놨는데, 이제야 측정 가능할 만큼 사실이 됐네요.

작은 심장마비가 하나 남아 있었습니다. 초록불이 뜬 뒤에도 `npm view @7onic-ui/react version`이 계속 0.3.6을 돌려줬거든요. 배포 로그에는 `+ @7onic-ui/react@0.3.7`, 그리고 작은 글씨로 "패키지를 처리 중이며 몇 분 뒤에 사용할 수 있습니다"라고 적혀 있었습니다. OIDC 배포는 처리 과정을 한 번 더 거치는데, 가장 큰 패키지는 30분쯤 걸렸습니다. 어떻게 아냐면, 그 30분 내내 시험 결과 발표 기다리듯 새로고침했거든요.

<br />

## 그리고 전부 지웠다

아직도 약간 이상한 기분이 드는 부분입니다. 좋은 쪽으로요. OIDC가 살아나자 제가 가진 npm 토큰은 전부 짐이 됐습니다. 짐보다 나빴어요. 그중 하나는 클립보드 소동 때 잠깐 채팅 세션을 평문으로 지나갔으니까요. 그래서 전부 폐기했습니다. GitHub의 `NPM_TOKEN` 시크릿도 지웠고(API로 확인하니 레포 시크릿 0개), 패키지마다 배포 권한을 "2단계 인증 필수, 2FA 우회 토큰 금지"로 바꿨습니다. 토큰으로 배포하는 길은 완전히 막히고, OIDC는 그대로 됩니다.

이제 npm 패키지 세 개의 배포 과정에는 어떤 종류의 자격 증명도 없습니다. 교체할 것도, 다섯 달 뒤 조용히 만료될 것도, 잘못 붙여넣을 것도 없어요. 제 파이프라인을 고친 건, 그 파이프라인에 인증하는 능력 자체를 없앤 일이었습니다.

<br />

## 지금 상황

CI에서 토큰으로 배포하고 계시다면 2027년 1월 차단은 여러분 얘기이기도 합니다. 저는 만료된 토큰과 제 클립보드 덕분에 석 달 일찍 문 밖으로 떠밀렸을 뿐이에요. 이미 GitHub Actions에서 배포하고 있다면 마이그레이션은 정말 한 시간 정도이고, 그중 대부분은 문서 읽는 시간입니다.

그렇다고 다 정리됐다고는 못 하겠습니다. 로그인 없는 파이프라인이 하루 종일 어색했어요. 이게 정말 우리라는 걸 증명하는 시크릿을 습관처럼 찾게 되더라고요. 이제 그건 없습니다. GitHub의 말이 증명이에요. 결국 "토큰 관리를 하는 나를 믿기"를 "OIDC 체인을 믿기"로 바꾼 셈인데, 이번 주 제가 토큰을 관리한 꼴을 보면 이건 고민할 거리도 아닙니다.

<br />

## 추가 (10월 17일): GhostAction이 더해 준 것

한 독자분이 10월 7일 무렵 다시 떠오른 GhostAction 공격(Socket이 붙인 이름이고, GitGuardian과 StepSecurity에도 분석 글이 있습니다)을 짚으면서 제 요점을 저보다 더 날카롭게 정리해 주셨습니다. 이 공격은 토큰이 필요 없습니다. 탈취된 관리자 계정이 가짜 `security-audit.yml`을 기본 브랜치에 바로 커밋하고, 그 워크플로가 푸시마다 실행되면서 레포의 모든 시크릿에 접근한 뒤, 작업 트리와 git 전체 이력에서 자격 증명처럼 보이는 걸 싹 긁어 갑니다. 그러니 피해 범위는 "교체한 그 토큰"이 아니었던 거죠. 심어진 순간부터 발견될 때까지 어떤 워크플로든 읽을 수 있었던 모든 시크릿입니다. 몇 년 전에 HEAD에서 지운 것까지 포함해서요.

그 댓글에서 이제 본문에 넣고 싶은 세 가지입니다.

1. **HEAD가 아니라 이력을 검사하세요.** 커밋됐다가 지워진 키도 객체 저장소에는 남아 있고, 이 변종은 거기서 읽어 갑니다.
2. **레지스트리 배포 토큰은 로그에 찍힌 적이 없어도 교체 목록에 넣으세요.** 워크플로가 읽을 수 있었다는 것 자체가 노출입니다. 로그는 상관없어요.
3. **yml을 지우는 건 0단계지, 해결이 아닙니다.** 그 파일은 배달 수단일 뿐이고, 모든 브랜치와 포크의 자격 증명 교체가 해결입니다.

그 관점으로 제 설정을 다시 확인했습니다. 레포 Actions 시크릿은 여전히 0개라 심어진 워크플로가 읽을 게 없습니다. npm의 Trusted Publisher는 `publish.yml`에 고정돼 있어서, 몰래 들어온 `security-audit.yml`은 `id-token: write`를 가져도 배포를 못 합니다. 기본 워크플로 권한은 읽기 전용이고요. 공개 레포, 비공개 원본 레포, 관계없는 프로젝트 하나까지 모든 브랜치의 전체 이력에서 GhostAction 파일 이름을 검색해 봤는데 아무것도 나오지 않았습니다.

그 댓글이 왔을 때까지 *안 한* 것도 있습니다. 워크플로 파일이 리뷰 없이 `main`에 들어가는 걸 막는 장치요. 그게 다음 할 일입니다. `.github/workflows/`에 대한 브랜치 규칙과 더 좁은 허용 액션 정책이 로드맵에 있고, 여기서 다른 모든 걸 잰 방식 그대로 잴 생각입니다. 직접 뚫어 보는 방식으로요.
