# [배포 회고] npm이 제 패키지가 없다고 했습니다 — 네 번의 실패와 토큰 0개

안녕하세요, 디자인 시스템 [7onic](https://7onic.design)을 만들고 있는 개자이너입니다.

10월 7일, `@7onic-ui/tokens@0.3.7`을 배포하려는데 npm이 이런 패키지는 없다고 했습니다.

```
npm error 404 Not Found - PUT https://registry.npmjs.org/@7onic-ui%2ftokens
npm error 404  '@7onic-ui/tokens@0.3.7' is not in this registry.
```

PUT 요청에 404라니요. 같은 워크플로로 이미 열 번 넘게 배포한 패키지였습니다. 릴리스 준비는 끝나 있었습니다. 세 환경 스모크 테스트도 통과했고, 배포 전 검사 17개도 통과했고, 체인지로그도 확정했습니다. 버튼만 누르면 되는 상황이었습니다. 그날 그 버튼을 네 번 눌렀고, 네 번 모두 실패했습니다. 에러도 매번 달랐습니다.

다음 날 저녁에는 배포 문제를 해결했습니다. 토큰을 새로 잘 만들어서가 아닙니다. **가지고 있던 npm 토큰을 전부 지우고, GitHub의 `NPM_TOKEN` 시크릿까지 없앴습니다.** 지금 레포에 등록된 시크릿은 0개이고, 배포는 전보다 더 잘 됩니다.

네 번의 실패를 순서대로 정리해 보겠습니다. 하나하나 별로 알고 싶지 않았던 걸 알려 줬습니다.

<br />

## 실패 1: 404인데 사실은 인증 실패

먼저 잘 알려지지 않은 사실 하나. **npm은 배포할 때 인증에 실패하면 404를 돌려줍니다.** 401이나 403이 아니라 "이 레지스트리에 그런 패키지 없음"이라고 나와서, 꼭 패키지 이름을 잘못 친 것처럼 보입니다. 권한 없는 사람에게 패키지가 있는지조차 알려 주지 않으려는 거라 이유는 이해가 갑니다. 하지만 내 패키지를 내 CI에서 배포하는 입장에서는, 멀쩡한 URL만 20분 동안 들여다보게 됩니다.

원인은 GitHub 시크릿 화면에 그대로 있었습니다. `NPM_TOKEN`의 마지막 수정일이 4월 9일이었습니다. 세분화된(granular) npm 토큰에는 만료일이 있는데, 그 뒤 다섯 달 사이에 조용히 만료돼 있었습니다. 4월 이후로 배포를 한 번도 안 했으니 아무도 몰랐습니다. 만료되는 날 경고가 뜬 것도 아니고, 제가 다음에 배포할 때까지 조용히 기다리고 있었던 겁니다.

<br />

## 실패 2, 3: 둘 다 제 실수

부끄러운 부분이라 한꺼번에 털어놓겠습니다.

새 토큰을 만들어서 `gh secret set NPM_TOKEN`으로 등록했습니다. 그런데 이 명령을 터미널이 아니라 AI 에이전트 세션 안에서 한 줄로 실행했습니다. 그러면 값을 붙여 넣으라는 입력 창이 뜨지 않고, 명령은 아무 문제 없다는 듯이 **빈 문자열**을 배포용 토큰으로 저장해 버립니다. 다음 실행은 `ENEEDAUTH`로 실패했고, 워크플로 환경 변수 목록에서 토큰이 아예 사라져 있었습니다. 패키지를 모두에게서 철저히 지켜 냈습니다. 저까지 포함해서요.

세 번째 시도에서는 클립보드 내용을 바로 시크릿에 넣었습니다. 그런데 npm 화면에서 드래그할 때 토큰 이름과 값이 한꺼번에 선택돼서, 클립보드에 둘이 붙은 채로 들어가 있었습니다. GitHub는 `7onic-gha-publish-2026-10npm_...` 같은 문자열을 그대로 저장했고, 워크플로는 그걸 그대로 넘겼고, npm은 당연히 알아보지 못했습니다. 또 404였습니다.

결정적인 단서는 토큰 상세 화면에 있던 **"Last used: never"** 한 줄이었습니다. 워크플로 로그에는 환경 변수가 들어가고 배포를 시도한 기록이 있는데, npm 쪽에서는 그 토큰이 한 번도 쓰인 적이 없다는 겁니다. 권한 문제가 아니라 애초에 엉뚱한 값이 들어가 있었던 겁니다.

(같은 실수를 막는 방법: 등록하기 전에 `pbpaste | head -c 4`를 실행해 보세요. `npm_`이 안 나오면 등록하지 마세요.)

<br />

## 실패 4: npm이 대놓고 알려 준 것

값을 제대로 넣으니 이번엔 처음 보는 에러가 나왔습니다. 이번에는 설명이 붙은 403이었습니다.

> Two-factor authentication or granular access token with bypass 2fa enabled is required to publish packages.

(배포하려면 2단계 인증을 하거나, 2단계 인증 우회가 켜진 세분화 토큰이 필요합니다)

새 토큰에는 예전 토큰에 있던 "2단계 인증 우회(bypass 2FA)" 체크가 빠져 있었습니다. 체크해서 다시 만들면 되겠다 싶었는데, 토큰 생성 화면에 경고가 떠 있었습니다. 2단계 인증 우회가 켜진 직접 배포용 토큰은 **2027년 1월부터 쓸 수 없다**는 내용이었습니다. 체크박스를 누르자 경고가 하나 더 떴습니다. "이 옵션은 보안 위험이 있습니다. 자동화나 CI/CD에는 Trusted Publishing을 사용하세요."

하루 동안 정리하면 이렇습니다. 토큰 방식은 서로 상관없는 네 가지 이유로 네 번 실패했고, npm은 빨간 경고로 두 번이나 이 방식이 석 달 뒤면 끝난다고 알려 주고 있었습니다.

Trusted Publishing은 언젠가 옮겨야지 하고 미뤄 둔 일이었는데, 더 미룰 수 없게 됐습니다.

<br />

## 옮기는 데는 세 번째 실패보다 시간이 덜 걸렸다

이번 일에서 가장 허무했던 부분입니다.

Trusted Publishing(프로토콜 이름은 OIDC)은 토큰을 공유하는 대신, npm이 GitHub에 "이 배포가 정말 이 레포의 이 워크플로에서 온 거 맞아?"라고 직접 확인하는 방식입니다. GitHub가 실행할 때마다 신원 증명에 서명하고, npm이 그걸 검증합니다. 만료될 토큰도, 붙여 넣을 시크릿도, 유출될 것도 없습니다. npm에서는 패키지마다 배포 주체를 한 번만 등록하면 됩니다. 소유자, 레포, 워크플로 파일 이름, 환경까지 네 칸입니다. 패키지가 세 개라 세 번 등록했습니다.

워크플로는 거의 지우기만 하면 됩니다. 배포 단계마다 있던 `NODE_AUTH_TOKEN` 환경 변수를 모두 지웁니다. 이게 중요합니다. 토큰이 남아 있으면 OIDC보다 먼저 쓰이기 때문에, 전환한 효과가 아무 경고 없이 사라집니다.

함정도 하나 있었습니다. Trusted Publishing은 **npm 11.5.1 이상**이 필요한데, Node 20 러너에는 npm 10이 들어 있습니다. 처음에는 `npm install -g npm@latest`를 넣으려고 했는데, 커밋 전에 확인해 보길 잘했습니다. 지금 `npm@latest`는 12.2.0이고 Node 22 이상을 요구해서, 제 러너에서는 설치부터 실패했을 겁니다. 그래서 11 버전대로 고정했습니다.

```yaml
- name: Upgrade npm for trusted publishing
  run: npm install -g npm@11 && npm --version
```

전환 작업은 이게 전부입니다. 등록 세 번, 환경 변수 삭제 세 군데, 버전을 고정한 업그레이드 단계 하나.

<br />

## 드디어 성공

10월 8일, 세 작업이 모두 통과했습니다. tokens는 18초, CLI는 16초, react는 4분이 조금 안 걸렸습니다. 토큰을 쓸 때는 없던 것도 생겼습니다. 배포할 때마다 워크플로 신원으로 서명된 출처 증명(provenance)이 붙고, Sigstore 공개 로그에 기록됩니다. 이제 누구나 `@7onic-ui/react@0.3.7`이 어떤 커밋에서, 어떤 GitHub Actions 실행으로 빌드됐는지 확인할 수 있습니다. README에 몇 달째 "공급망 검증"이라고 적어 놨는데, 이제야 그 말이 제대로 사실이 됐습니다.

마지막으로 한 번 더 철렁한 일이 있었습니다. 성공한 뒤에도 `npm view @7onic-ui/react version`을 치면 계속 0.3.6이 나왔습니다. 배포 로그에는 `+ @7onic-ui/react@0.3.7`이 찍혀 있었고, 그 아래 작은 글씨로 "패키지를 처리하는 중이라 사용할 수 있게 되기까지 몇 분 걸릴 수 있다"고 적혀 있었습니다. OIDC로 배포하면 처리 단계를 한 번 더 거치는데, 가장 큰 패키지는 30분 정도 걸렸습니다. 그 30분 동안 합격자 발표 기다리듯 계속 조회해 봤기 때문에 정확히 압니다.

<br />

## 그리고 토큰을 전부 지웠다

지금 생각해도 묘하게 기분 좋은 부분입니다. OIDC가 돌아가기 시작하자 가지고 있던 npm 토큰은 전부 필요 없어졌습니다. 필요 없는 정도가 아니라 위험했습니다. 그중 하나는 클립보드 소동 때 채팅 세션에 그대로 노출됐었으니까요. 그래서 토큰을 모두 폐기했습니다. GitHub의 `NPM_TOKEN` 시크릿도 지웠고(API로 확인해 보니 레포 시크릿 0개), 패키지마다 배포 설정을 "2단계 인증 필수, 2단계 인증 우회 토큰 사용 금지"로 바꿨습니다. 이렇게 하면 토큰으로는 아예 배포할 수 없고, OIDC 배포는 그대로 됩니다.

이제 npm 패키지 세 개를 배포하는 과정에는 비밀번호도 토큰도 하나도 없습니다. 주기적으로 바꿀 것도, 다섯 달 뒤에 몰래 만료될 것도, 잘못 붙여 넣을 것도 없습니다. 배포 파이프라인을 고친 방법이, 결국 파이프라인에 로그인하는 수단 자체를 없애는 거였습니다.

<br />

## 정리하며

CI에서 토큰으로 배포하고 있다면 2027년 1월 차단은 남의 일이 아닙니다. 저는 만료된 토큰과 제 클립보드 실수 덕분에 석 달 먼저 옮겼을 뿐입니다. 이미 GitHub Actions에서 배포하고 있다면 전환은 한 시간 정도면 되고, 그중 대부분은 문서를 읽는 시간입니다.

그렇다고 마음이 완전히 편한 건 아닙니다. 로그인 없이 돌아가는 파이프라인이 하루 종일 어색했습니다. 우리가 배포한다는 걸 증명해 줄 토큰을 자꾸 찾게 되는데, 이제 그런 건 없습니다. GitHub가 보증해 주는 것이 곧 증명입니다. "토큰을 잘 관리하는 나"를 믿는 대신 "OIDC"를 믿기로 바꾼 셈인데, 이번 주에 제가 토큰을 관리한 꼴을 생각하면 고민할 필요도 없는 선택이었습니다.

<br />

## 추가 (10월 17일): GhostAction 사례를 보고

한 독자분이 10월 7일 무렵 다시 퍼진 GhostAction 공격(Socket이 붙인 이름이고, GitGuardian과 StepSecurity에도 분석 글이 있습니다)을 알려 주셨는데, 제가 하고 싶던 말을 저보다 더 정확하게 짚어 주셨습니다. 이 공격은 토큰을 훔칠 필요가 없습니다. 탈취한 관리자 계정으로 가짜 `security-audit.yml`을 기본 브랜치에 바로 커밋합니다. 그러면 이 워크플로가 푸시할 때마다 실행되면서 레포의 시크릿을 전부 읽고, 작업 폴더와 git 전체 이력을 뒤져 인증 정보처럼 보이는 걸 모조리 가져갑니다. 그러니 피해 범위는 "교체한 그 토큰 하나"가 아닙니다. 공격 파일이 들어온 순간부터 발견될 때까지 워크플로가 읽을 수 있었던 모든 시크릿, 몇 년 전에 지운 것까지 전부입니다.

그 댓글을 보고 본문에 꼭 넣고 싶어진 내용이 세 가지입니다.

1. **현재 코드만이 아니라 전체 이력을 검사해야 합니다.** 커밋했다가 지운 키도 git 저장소 안에는 남아 있고, 이 공격은 거기서 꺼내 갑니다.
2. **배포 토큰은 로그에 찍힌 적이 없어도 교체 대상입니다.** 워크플로가 읽을 수 있었다는 것 자체가 노출입니다. 로그에 찍혔는지는 상관없습니다.
3. **yml 파일을 지우는 건 시작일 뿐 해결이 아닙니다.** 그 파일은 공격을 실어 나른 수단일 뿐이고, 모든 브랜치와 포크의 인증 정보를 교체해야 해결입니다.

이 기준으로 제 설정을 다시 확인했습니다. 레포의 Actions 시크릿은 여전히 0개라, 공격용 워크플로가 들어와도 읽을 게 없습니다. npm의 Trusted Publisher는 `publish.yml`에만 연결돼 있어서, 몰래 넣은 `security-audit.yml`은 `id-token: write` 권한이 있어도 배포를 못 합니다. 워크플로 기본 권한도 읽기 전용입니다. 공개 레포, 비공개 원본 레포, 관계없는 프로젝트 하나까지 모든 브랜치의 전체 이력에서 GhostAction 파일 이름을 검색했는데 하나도 나오지 않았습니다.

댓글을 받은 시점까지 아직 못 한 일도 있습니다. 워크플로 파일이 리뷰 없이 `main`에 들어가는 걸 막는 장치입니다. 이게 다음 할 일입니다. `.github/workflows/`에 브랜치 규칙을 걸고 허용하는 액션을 더 좁히는 작업을 로드맵에 올려 두었습니다. 이것도 지금까지처럼 직접 뚫어 보는 방식으로 확인할 생각입니다.
